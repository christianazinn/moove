# Architecture

```
┌──────────────────────────┐   subscribe + call reducers   ┌───────────────────────────────┐   subscribe + call reducers   ┌──────────────────────────────┐
│ iOS app (SwiftUI)        │ ────────────────────────────▶ │ SpacetimeDB module (TS)       │ ◀──────────────────────────── │ Agent worker (Node/TS)       │
│  RoomPlan scan           │                               │  tables  = shared world state │                               │  pricing / sort / listing /  │
│  photo capture           │ ◀──────── live updates ────── │  reducers = every write       │ ─────── live updates ───────▶ │  buy / fraud / vision agents │
│  review, spend log,      │                               │  (maincloud; no outbound I/O) │                               │  Claude, Apify, x402 + CDP,  │
│  approvals, new home 3D  │                               └───────────────────────────────┘                               │  eBay sandbox, Visa, Auth0   │
│  Auth0.swift login       │ ── Auth0 ID token (OIDC) used as the SpacetimeDB identity                                     │  CIBA, file upload endpoint  │
│  MooveKit (pure Swift)   │ ── photo / USDZ upload over HTTP ───────────────────────────────────────────────────────────▶ └──────────────────────────────┘
└──────────────────────────┘
```

## Components
**iOS app (`ios/`).** SwiftUI, iOS 17+, Swift 6. It is the only client.
- RoomPlan (`RoomCaptureView` / `CapturedRoom`) exports the room as USDZ plus the object list. **It needs a physical LiDAR iPhone; the Simulator can't scan.**
- Photo capture for item details.
- RealityKit for the new-home view and the fly-in animation.
- Auth0.swift for login.
- `MooveKit/` is a local Swift package: models that mirror the SpacetimeDB tables, plus pure algorithms (layout solver, volume/truck estimate, packing). It has no UIKit/RealityKit dependencies, so `swift test` runs on Linux too.
- The project is generated by **XcodeGen** from `ios/project.yml`. `*.xcodeproj` is gitignored, which avoids pbxproj merge conflicts.

**SpacetimeDB module (`spacetime/`).** A TypeScript module, and the **system of record and the contract** (see `data-model.md`).
- Reducers are the only way to write. They stay deterministic, with no network calls.
- The app and the worker both subscribe to the tables, which is what gives us two-screen live sync and the live spending log.
- Identity: clients connect with an Auth0-issued OIDC token. Reducers authorize writes by `ctx.sender`. The worker connects with its own service identity.

**Agent worker (`agents/`).** A Node/TS process connected to SpacetimeDB as a client through generated bindings (`spacetime generate --lang typescript`).
- It subscribes to rows needing work (unpriced items, sell items without listings, approved approvals, open shopping-list entries). Each agent runs, then writes results back via reducers.
- Every step becomes an `agentEvents` row: plan, tool call, payment, result, error.
- All outbound I/O lives here:
  - Anthropic SDK (vision, sorting, listing copy, agent loops)
  - Apify (comps from Facebook Marketplace / Craigslist / eBay, deal search, later Zillow)
  - x402 + CDP wallet on Base Sepolia (agents pay per call, with spend caps)
  - eBay Sell API sandbox
  - Visa (Starter Pack tooling)
  - Auth0 async authorization / CIBA (phone approval)
- It hosts a small HTTP upload endpoint for photos and USDZ files, because SpacetimeDB isn't a blob store. Files start on local disk and can move to object storage if needed. Rows store URLs.
- It runs on a laptop for development. For the demo it can stay on a laptop, or move to a small VM so it keeps working with the lid closed.

## Key flows
1. **Scan → inventory:** RoomPlan output is uploaded and `createScan` / `upsertItemsFromScan` are called. The worker's vision agent enriches each item from its photos.
2. **Pricing:** the worker sees items with no `estValue`. The pricing agent pays for comps over x402 (logged to `payments` + `agentEvents`), fetches comps through Apify, and sets the value. The sort agent then sets the disposition, skipping `maybeSentimental` items.
3. **Sell:** a sell item with no listing gets a draft listing from the listing agent. If the price is above the threshold, the worker creates an `approvals` row and sends an Auth0 CIBA push. Once approved, the listing posts to the eBay sandbox.
4. **Buy:** for each open shopping-list item, the buy agent searches deals through Apify, then the fraud screen runs (stretch), then Visa checkout (with approval if above the threshold).
5. **New home:** the demo house comes from fixtures (Zillow later). The layout solver in MooveKit places kept and bought items, and RealityKit runs the fly-in.

## Top risks and fallbacks
| Risk | Mitigation / fallback |
|---|---|
| **No official Swift SpacetimeDB SDK** (only the community `ekscrypto/spacetimedb-swift-sdk`) | Hour-0 spike by the iOS capture lane: connect, subscribe to `items` and call one reducer. If it fails, the worker exposes a thin WebSocket/REST gateway that relays subscriptions and reducer calls, and SpacetimeDB stays the core. |
| RoomPlan scan quality / demo-room access | Record the demo scan early (#3) and commit the export to `agents/fixtures/`. |
| Scrapes slow or blocked during the demo | Cache Apify results to fixtures and replay them when live calls fail (label the replay). |
| x402 / CDP testnet hiccups | Keep a funded Base Sepolia wallet. Payments carry a `simulated` flag that the UI shows when used. |
| eBay / Visa sandbox onboarding delays | Start signups immediately. Each integration sits behind an interface in `agents/src/integrations/` with a labeled simulated implementation. |
| Zillow floor plans | Hardcoded demo house first. Zillow only if there's time. |
